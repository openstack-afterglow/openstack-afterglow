## Why

The console exposes only project selection in global chrome and sends domain switching/creation to a separate sidebar destination. Users need one GCP-style resource selector and a coherent domain IAM model: authorized domains, their authorized projects, personal presentation preferences, delegated project lifecycle, unique ownership, new-user personal domains, email membership and domain quota allocation with truthful usage monitoring.

## What Changes

- Replace the existing selector with a shared viewport-bounded resource dialog reached from the top-left at every breakpoint and from the existing mobile drawer. The dialog contains a domain picker, project search, recent/pinned/all views, stable UUIDs, new project/domain entry points and presentation settings. Selecting a domain for browsing must not silently change the active session. Committing a project must use server-validated domain/project scope and preserve original identity/session lifetime, pending invitation/MCP intent, Cloud Shell closure and ABA/late-response fences. Domain-only work remains possible for managers without a selected ordinary project. Remove the sidebar domain-switch/create destination; the login continuation route may reuse the same shared selection surface.
- Only current created/joined/home domain membership and actual project membership may populate the user selector; system-admin global observation is a separate surface, not a selector bypass. Manager visibility is all enabled projects in their domain through the existing native manager access contract. Revoked/foreign inventory cannot be restored by presentation preferences or caches.
- Persist per-user domain/project pin, order and hidden settings independently of authorization, keyed by UUID. Hidden resources remain recoverable in explicit display settings; active scope must remain named and never be silently changed by hiding it.
- Add explicit domain-scoped project_creator capability using the current native role-ID graph, without seeding grants at login/startup. User decision: creation in the current domain is allowed; deletion requires both creator capability and current sole ownership. Domain managers retain domain-wide management. Default and projects with resources, child projects or unavailable deletion checks remain undeletable. No force or resource teardown.
- Every new domain has canonical Default. Every signup/invitation acceptance grants Default project_reader immediately, not only at a later login. Existing-user domain invitations retain the original identity and add membership in the invited working domain. Invitation redemption remains one-use, durable, fenced and compensatable; account/role native uncertainty must not trigger blind retries.
- New ordinary project creation assigns its creator as the single explicit project_owner. Ordinary admin/member/reader grades may have multiple members. Ownership transfer must be explicit and reject a second owner, group/inherited owner creation and changes removing the last owner. manager > owner is domain administrative precedence, NOT a global manager→project_owner inference edge that would create multiple owners. Preserve the existing owner→admin→member→reader native DAG. Existing multi-owner projects require explicit resolution; do not silently select/revoke an owner.
- User decision: personal-domain provisioning applies only to NEW human users. Their creation/registration forms require a personal domain display name; existing users/service accounts are not moved or automatically provisioned. Each new user's immutable native identity is created in their personal domain, they manage its Default, and joining another domain adds Default reader there. Existing users can accept cross-domain invitations without a new identity. All target-domain IAM directories/project invitations must recognize explicit joined users, not merely native home-domain users, while password/profile administration remains home-bound.
- Domain UUID is identity. Keystone's native domain name is globally unique, so new managed domains use an opaque unique internal name and a nonunique user-facing display-name attribute. Centralize display extraction/resolution; existing native domains keep their existing name as display fallback. Native auth/scope always uses ID. Ambiguous display-name login resolution must fail clearly and request ID, never choose an arbitrary same-name domain. Do not rename existing native domains or change operator config.
- Project owner/admin can add or invite already-joined same-domain users to that project, using existing grade/role ceilings. Domain managers invite an email into the domain, optionally selecting an additional project/roles; Default reader does not require choosing another project. Existing identities must not be recreated or have passwords changed.
- System:all admin retains explicit domain filtering and monitoring of domains/projects/groups/users/application credentials and safe credential metadata. Domain managers get domain IAM users/projects/quotas/usage/resources; they never receive system administration or another domain's inventory/secret material.
- User decision: domain quota is an allocation budget: the sum of native per-project limits must stay within the system-admin-set domain ceiling. Manager sets project limits and future-project defaults within that ceiling. Defaults do not overwrite existing projects. Unlimited, zero, unknown/unavailable, used/reserved and limit remain distinct. Concurrent allocations must serialize under a domain mutation boundary and failures/partial native writes require readback/recovery, not pretend transactions. Integrate every affected Afterglow project-create/quota-write path so another first-party API cannot bypass the budget. External native administrators can cause drift; detect and surface it rather than claiming universal native domain usage enforcement. Resource categories reuse the current native quota capabilities; unsupported attribution/service data are explicitly unavailable, never measured zero.
- Domain IAM monitoring includes actual per-project quota/usage and per-user membership/attributable usage plus domain resource inventory. Reuse existing domain_monitoring/native quota adapters and shared Bklit numeric primitives. Do not invent per-user native quota enforcement where the service exposes only project limits.

## Capabilities

### New Capabilities

- Unified domain/project resource navigation and durable user display preferences.
- Domain allocation budgets, per-project delegation/defaults and manager usage/resource observation.
- New-human personal domains with duplicate display names and explicit unique project ownership.

### Modified Capabilities

- Domain enrollment, working-domain membership, project creation/deletion, owner transfer and role mutations.
- Existing auth selection routes, domain IAM, system-admin domain observation and four-locale responsive UI.

## Impact

Backend identity/auth/project/quota/enrollment services, SQL models/migrations and API contracts; frontend shared chrome, selectors/onboarding/IAM/admin domain surfaces and ko/en/ja/zh-CN catalogs. Root ARCHITECTURE.md, DESIGN.md and relevant existing API/testing/deployment docs must be synchronized after runtime qualification. Reuse existing primitives, current native authority and durable operation patterns; no parallel authorization model.

Work only on shared dev and preserve unrelated changes/index, private credentials, keys, existing native grants/data and volumes. No production writes or deployment, automatic role preset application, existing-user personal-domain migration, existing owner revocation, force deletion, paid provider calls or relaxed cloud security. New-role setup is an explicit administrator workflow. Any local target connected to the real cloud is observation-only for this feature; destructive/provisioning acceptance uses an isolated local canonical Compose deployment with real SDK/SQL/Redis and a synthetic native service boundary.

Completion requires endpoint regressions and relevant named/full gates, actual API/SQL/SDK smoke, compiled browser interaction/screenshots across four locales, dark/light and mobile/tablet/desktop, all affected canonical image target architectures and deployed local readiness/smoke, architecture guard, truthful evidence/limits and OpenSpec archive. Existing outside-scope failures remain explicit rather than weakening tests or guardrails.
