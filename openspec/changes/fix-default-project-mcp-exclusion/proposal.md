## Why
Each domain's `Default` project is the system-owned domain-authority project (created by `domain_projects._bootstrap`, enabled once its grants are in place). It must not be reachable through MCP, and its name must stay system-reserved. Separately, `ec82f9da` widened Afterglow's own project-write gates to `{admin, manager, member}` for every surface; the owner clarified that the manager-as-member behaviour belongs only to Drover, Waygate, Palimpsest and Lumen, whose own policies already include `manager`, and that `manager` is assignable only on `Default` where it carries domain-wide authority.

## What Changes
- MCP never connects a project named `Default` (surrounding whitespace and case ignored): it is dropped from project discovery (`/auth/mcp-projects`, preview included) and from `all` candidates, rejected for `selected` and for a `current` working project, rejected at OAuth approval and personal-key issuance, and a stored grant whose approved project name is `Default` is refused when it is used. Because pre-migration grants saved the bare project ID as the name, `connection._validate_current_roles` also refuses a connection whose live token project name is `Default`, before any native call. Existing grants are neither deleted nor revoked.
- One helper, `domain_projects.is_reserved_default_name`, decides the reserved name for user project creation, administrator project creation and renaming another project to `Default`. The previous `casefold()`-only comparison did not recognise names with surrounding whitespace.
- `service_permissions.PROJECT_WRITE_ROLE_NAMES` returns to `{admin, member}`. The web write gate, Cloud Shell write re-check and frontend `canWrite` fallback return to their behaviour before `ec82f9da`. MCP had inlined `{admin, manager, member}` before that commit and now uses the same shared set, so `manager` no longer counts as manageable there; this has no practical effect because `manager` exists only on `Default`, which MCP no longer connects. MCP `access_level` stays `read|manage`.
- No schema, role-graph, grant, native-policy, deployment or version change. "manager only on Default" and its domain-wide effect are already enforced by `manager_requires_default_project`, `test_manager_assignment_and_inference_addition_are_Default_only` and `test_read_manager_is_Default_effective_not_home_domain_or_admin`; they are cited, not re-implemented.

## Impact
MCP keys and OAuth grants can no longer include a domain's `Default`; an existing grant limited to `Default` stops working but remains visible until the owner removes it, including pre-migration grants that stored only a project ID. The rule is by name and applies to every domain, so a personal domain created by the earlier enrollment flow, whose only project is named `Default`, can no longer be used through MCP; projects generated today by `account_spaces.project_name` are named `<name>-<random>` and are unaffected. The number of such legacy accounts in any deployment was not checked. A web user holding only `manager` is read-only for project resources, as before `ec82f9da`. Native service policy is separate and unchanged.
